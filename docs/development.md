## 開発の手順

```
npm test        # node --test
npm run build   # plugins/project-board/assets/project-board.html（プラグインに同梱する完成版）を作る
```

- `plugins/project-board/src/` を変えたら `npm run build` を実行し、`assets/project-board.html` をコミットする。古いと `npm test` が失敗する。
- GitHub Actions（`.github/workflows/test.yml`）が、`main` への push と pull request で、Windows・Node 24 の `npm test` を実行する。`engines`（`plugins/project-board/package.json`）は `>=24`（README の「24 で動作確認」と同じ。それより古い版は未確認）。`engines` は npm の警告にしかならず、`node` の実行は止めない。ワークフローの実行は、GitHub 上では未確認。
- このリポジトリを直接開いてプラグインを試すときは、`claude --plugin-dir ./plugins/project-board` で起動する。
- 環境変数 `PROJECT_BOARD_HOME` は、プラグイン専用のフォルダ（`${CLAUDE_PLUGIN_DATA}`）の場所を固定する。テストと開発用。`--plugin-dir` で読み込むと置き場が本番と別（`project-board-inline`）になるので、開発時はこれで固定する。

### リリースの手順

push のたびには `version` を上げない。リリースするときだけ、次の順で行う（グローバルの git-flow.md の段階 9 に、project-board 固有の手順を足したもの）。

1. **version を上げる**: リリースする版（例: `v1.1.0`）が決まったら、その版の `v` を除いた数字に、次の 3 か所を合わせる。上げる PR は、リリースする変更の PR か、そのすぐ後の PR にする。
   - `plugins/project-board/.claude-plugin/plugin.json` の `version`（変えないと、利用者に更新が届かない）
   - `plugins/project-board/package.json` の `version`（`plugin.json` と同じ値。`tests/plugin.test.js` が一致を確かめる）
   - `tests/plugin.test.js` の `assert.equal(plugin.version, "…")`（固定値）
2. **マージしてからタグを打つ**: タグ（`vMAJOR.MINOR.PATCH`）は、version を上げた PR のマージ後の `origin/main` に付ける。version を上げる前のコミットに付けない。付けたあとで食い違いに気づいたら、タグと GitHub Release を付け直す前に、ユーザーに確認する。
3. 版の決め方・タグ・GitHub Release（`gh release create <版> --generate-notes`）は、git-flow.md の「リリースするとき」に従う。`docs`・`chore` だけのときは、版を上げず、リリースしない。

## 設計判断

- **作業枠（`sessions`）の ID の重複は、`validate` で warning にする**: 枠の移動・確認・削除は ID だけで探すので、重複すると両方に効く。error にすると、すでに重複したデータが保存できなくなり、直す手段（CLI も画面も保存に失敗）が無くなるため、warning にとどめた。
- **変更履歴（`changeLog.taskIds`）に、消したタスクの ID が残っても注意にしない**: タスクを消しても変更履歴は残す（ID を使い回さない採番が、消したタスクの履歴が残ることを前提にしている）。以前は `validate` が「changeLog: 存在しないタスク」の warning を出していたが、日程変更のあったタスクを画面で消すと、以後ずっとバナーに出て、画面からは消せず、何もこの注意を読んで動かないため、消した。
- **依頼のやりとり（`thread`）の件数に上限を置かない**: 以前は 40 件で例外にしていた。やりとりは、聞き返し（エージェント）と返信（利用者）が交互にしか足せない（状態の遷移の表）ので、40 件は同じ依頼で 20 往復になり、1 人で使う道具では起こらない。起こっても 1 件の依頼が長くなるだけなので、上限を消した。履歴の 20 件（`pruneRequests`）と、1 件の文章の 4000 文字（貼り付けたメール・議事録の大きな本文を防ぐ）は残す。

- **タスクの ID は、消したあとも使い回さない**: 採番は、いまのタスクと変更履歴（`changeLog.taskIds`）の ID の最大番号 + 1（`edit.js` の `nextTaskId`）。「タスク数 + 1」だと、最後のタスクを消して足したとき同じ ID に戻り、消したタスクの変更履歴が、新しいタスクのものとして出た。見送った案: 採番の番号をデータに持つ（形式が増える）。履歴に残らない（変更履歴に載っていない）タスクの ID は、使い回されてもよい（何も参照しないため）。
- **予定表の取り込みは、別のエージェント（`intake-calendar`）にして、Excel と規則の `intake` は `tools: Read, Write, Bash` に絞る**: 予定表の件名・本文は、会議の招待を送る外の人が書ける。`calendar-auto` は承認なしで書くので、中に「メールを送れ」のような指示があっても、ツールが無ければ実行できない形にしたい。ただし予定表の MCP のツール名は利用者が決めるので、予定表側は `tools` を省略して全ツールを引き継ぐ（名前を前もって書けない）。そのため、予定表側の入口は、本文の「読むだけのデータ」の規則だけで守っている（**予定表の件名経由の経路は残る**）。見送った案: 予定表の取得をスキル側（メインの会話）で行い、`fetched.json` だけをエージェントに渡す（見張りの手順が大きく変わる）。MCP を絞って渡す方法は、Claude Code の仕様を確かめていない（未確認）。
- **`project-board-mcp.json` は、一時ファイルに書いてから置き換える**: 書き込みの途中で止まっても、予定表の取り込みが全部止まる壊れ方をしないため（`data.json` の保存と同じ方針）。

- **プロジェクトの期限を、タスクの最終期限から決める**: 依頼文に日付がなく、タスクの案と一緒に決まるため、依頼で期限を必ず指定させる案は見送った。期限は、承認前の提案カードで確認して、「修正を依頼する」で直せる。
- **マイルストーンの警告は、プロジェクトの期限を超えるときだけ**: 日付を動かしたときに「後ろにタスクが残る」ことで警告する案は見送った。途中の節目（例: 機器発注）の後には、いつもタスクが残るため、毎回警告が出て意味がなくなる。
- **1 人で使う前提**: 複数人が同じ `data.json` を同時に編集する用途は想定しない。保存前に更新日時を比べ、他の更新があれば最新のファイルに同じ編集を当て直して保存する（ロックはしない）。
- **スキルの起動**
  - `intake` のスキルには `disable-model-invocation` を付けていません。自然な言い方で起動してよく、データを書くのは変更案を見せて承認を得たあとだけだから。
  - いずれも、変更案を示して承認を得てからデータを書き換える。書き込みは CLI（`tools/inbox.js`・`tools/intake.js`）に任せ、CLI が書く前に検証（`validate`）し、通ったときだけ書く（通らなければ何も書かない）。`intake`・`intake-calendar` のエージェントは、書き込んだ後に `validate.js` を実行しない（書けた後に `errors` は出ないので、同じ検証の二重になるため。以前は実行して報告していた）。エージェントが `data.json` を直接書き換えることはない。日程の変更・文章の取り込みは、受信箱の経路（HTML の帯 → `inbox` エージェントの `propose` → `approve`。「HTML からの依頼（inbox）」を参照）で行う。
  - `doctor`・`init`・`mcp`・`watch` は `disable-model-invocation: true`（利用者が明示して呼ぶ）。`doctor`・`init`・`mcp`・`watch` は、自分のスクリプトだけを `allowed-tools` で事前に許可している。
- **画面の編集では前後のタスクを見ず、前後の見直しを Claude Code の依頼に寄せた**: 画面での期限・開始日の変更に確認パネルを挟むと、1 件を直すたびに手が止まるため。前のタスクの期限を見て、次のタスクをまとめて動かす判断は、原因と理由を残せる依頼の処理に集めた。代わりに、画面から変えた日程は履歴に残らず、次のタスクとの食い違い（次のタスクの期限が前のタスクより前になる）も画面は警告しない。
- **入口を HTML の依頼に寄せた**: 日程の変更・文章の取り込み・タスクやプロジェクトの変更を、コマンド（`replan`・`inbox`）ではなく、HTML の「Claude Code に依頼する」から行う。入口が 3 つ（コマンド・画面の編集・依頼）に分かれていて、どれを使うか分かりにくかったため。手動で依頼を処理する入口（`/project-board:inbox`）は設けず、処理は `/project-board:watch` の見張りが行う。見張りが止まっている間、依頼は処理されない。見送った案: 手動の入口を残す（コマンドが増え、入口の整理にならない）。
- **祝日の更新を `holidays.js ensure` に置いた**: 更新の判定（未取得・取得から 30 日超・一覧の最終日が今日以前・提案が使う日が一覧の範囲外）を `needsHolidayUpdate` の 1 か所に置き、`propose` と `ensure`（`watch` を始めるとき）が同じ判定を使う。判定をエージェントの指示（Markdown）に書くと、実行のたびにぶれるため。見送った案: Claude Code の起動時（`SessionStart` フック）に取得する（毎回の起動でネットワークに出る。フックの設定が増える）。
- **土日祝を営業日に数える設定を `data.json` ごとに 1 つにした**: `settings.countWeekendsAndHolidays`（`true` のときだけオン）。仕事用とプライベート用で `data.json` を分けて使うため、プロジェクトごとの切り替えは要らない。オンのとき、土日と日本の祝日を営業日に数え、手動の休み（`holidays`）は飛ばす。切り替えは HTML の設定タブ（「基本の設定」の先頭の行「営業日の数え方」）だけで行う。見送った案: 土・日・祝日を別々に選ぶ（まとめて足りる）、プロジェクトごとの切り替え（`data.json` を分けるので不要）、依頼からの切り替え（設定は画面で変える方針）。
- **`intake` スキルは自動起動を外さない**（`disable-model-invocation` を付けない）: 「予定表を取り込んで」のような依頼で、モデルが起動できるようにするため。書き込みは承認の後だけで、`calendar-auto` が承認なしで書くのも、追加と、終わっていない未確認の会議の更新・削除だけ。外部への送信はしない。plugin-rules.md の B4 の「不可逆な書き込み」に当たるかは解釈が分かれ、例外として扱う。見送った案: 手動起動に限る（依頼から起動できなくなる）。
- **MCP を同梱しない**
  - 予定表の MCP（Outlook など）は、利用者が Claude Code に用意したものを使う（`.mcp.json` はない）。
  - 指定は `/project-board:mcp` で `${CLAUDE_PLUGIN_DATA}`（`~/.claude/plugins/data/` の下）の `project-board-mcp.json` に保存し、`data.json` には入れない。
  - このファイルには `schema_version`（現在 1）を入れる。無いファイルは古い形式として、読まずに「project-board-mcp.json（<パス>）を削除してから、/project-board:mcp で指定し直してください」のエラーにする（利用者の判断: 古い形式への互換性は不要）。`/project-board:mcp` の保存（`set`・`clear`）も、このファイルを読むので同じエラーで止まる。そのため、パスを示して、先に削除するよう案内する。保存形式を変える版では、この節に移行手順を書く。
- **レポート（共有用 HTML の保存）を機能ごと消した**: 1 人で使う前提で、共有用の HTML を出す手段は要らない。レポート専用の `core/reportspec.js`・`ui/views/report.js`・`ui/views/reportpanel.js`・`ui/savefile.js`、`prefs.js` の記憶、`gantt.js` の `readonly` 引数を消した。`data.json` の `settings.reportShowMeetingTitles` は、残っていても検証が何も言わない（データからは消さない）。見送った案: 読み取り専用のガントだけ残す（使う画面がなくなるため）。
- **SharePoint Online 上の `data.json` は、ネットワークドライブ経由で使う。https の URL での読み書きは対応しない**: `data.json` をローカルに置けない利用者がいるため。画面は `showOpenFilePicker`・`createWritable`・`lastModified` だけを使い、ファイルの場所を区別しない（`store.js`）ので、割り当てたドライブのファイルを選べば、コードの変更なしで使える見込み。README に手順を書いた。見送った案: Microsoft Graph での読み書き（Entra ID へのアプリ登録と権限の許可が要り、利用者は管理者に頼めるか不明。ログインの戻り先に `file://` を使えないので、HTML を置く https の場所も要る。競合の検知を ETag に、自動の読み直しを Graph 向けに作り直す必要がある）、Power Automate を間に挟む案。未確認: ネットワークドライブの `data.json` を、ブラウザの「ファイルを開く」で選べるか・保存できるか。WebDAV の遅さが自動の読み直し（4〜16 秒ごと）に与える影響。CLI（`tools/cli.js` の置き換え保存）・`/project-board:watch` がこのドライブで動くか。
- **外部パッケージを使わない**: ローカルサーバー・常駐プロセス・データベースも使わない。Excel の取り込みだけ、Python の `openpyxl`（システムのもの、または専用の venv `<置き場>/venv` のもの）を使う。
- **データファイル（`data.json`）の書き込みは、置き換え**: CLI（`tools/cli.js` の `save`）は、同じフォルダの一時ファイルに書いてから `renameSync` で置き換える。途中で止まっても元のファイルが壊れないようにするため（`.project-board/` は `.gitignore` の対象で、Git に履歴がない）。置き換えは、100 ms 待って最大 3 回試す（`renameWithRetry`。ウイルス対策ソフトなどが一時的に開いている場合に備える）。3 回とも失敗したとき（ほかのプログラムが開いている、など）は、「置き換えられませんでした」の例外にして、`data.json` は元のままにする（直接の上書きはしない。上書きの途中で止まるとファイルが壊れるため）。やり直しの待ちが足りるかは、実機では未確認。OneDrive などの同期フォルダでは、同期ソフトが一時ファイルを掴んで置き換えに失敗し、毎回このエラーになる可能性がある（未確認）。一時ファイルは、成功・失敗のどちらでも消す（消せなくてもエラーにしない）。ブラウザの保存（`store.js`）は変えていない。File System Access API の `createWritable` は、閉じるまで一時の場所に書いて、閉じたときに置き換える仕様（この環境では動作を確かめていない。未確認）。
- **Excel 用の openpyxl は、システムにあれば使い、無ければ専用の venv `<置き場>/venv` か、システムの Python のユーザー領域のどちらかを選んで入れる**
  - 探す順: ① システムの Python が、固定した版と同じ 3.x 系（`3.1.x`）の `openpyxl` と、`et_xmlfile`・`defusedxml` を import できる → それを使う（何も入れない。承認も要らない）。② `<置き場>/venv` の Python が動き、固定した版（`==3.1.5`）の `openpyxl` を import できる → その Python で読む。③ どちらも無い → 入れ先（既定は venv、`--system` はシステムのユーザー領域）を選び、承認（`--yes`）のあとで入れる。
  - venv の入れ方: 作成元の Python（`choosePython` が選ぶ）で `python -m venv <置き場>/venv` を作り、その venv の Python で `pip install --quiet --require-hashes -r requirements.txt` を実行する。版とハッシュは `requirements.txt` で固定する（ハッシュは PyPI の配布ファイルから `pip hash` で求めた値）。入れる前に、場所と内容を示して承認を求める。
  - 専用フォルダ `project-board-pylib`（`pip install --target`）から venv に戻した理由: 他のプラグイン（`pptx-deck`・`vault-kb`）が、同じ `<置き場>/venv` を使い、`setup [--yes]`・`doctor` の形も同じ。方針をそろえ、利用者が 1 つのやり方で覚えられるようにするため（利用者の判断）。以前は、利用者の Python に `venv`・`ensurepip` を求めることと、壊れた venv の作り直しの分岐が要ることを理由に外した（現在は作り直しの分岐そのものを持たない）が、作成元に `venv`・`ensurepip` が無いときは `--system` か CSV を案内する形で、受け入れた。
  - `<置き場>/venv` が既にあって使えない（壊れた・版のずれた・利用者自身の venv）ときは、**消さずに**、パスを示して「project-board が作ったものなら消して、ほかのものなら移動してから、もう一度」と案内し、終了コード 3 で止まる。project-board は、既にあるフォルダを消さない。消すのは、この実行で `python -m venv` を始めたフォルダ（直前に無かったもの）を、作成や pip install に失敗したときだけ（`rmSync` の `maxRetries: 3`）。理由: 壊れる・版がずれるのは、基底の Python を消したときと、固定した版を上げたときだけで、起きても利用者がフォルダを消せば直る。以前は、project-board が作った印のファイル `project-board-venv.txt` があるフォルダだけを自動で消して作り直していた（印を先に書く・リンクと空のフォルダの判定・消せないときの案内）が、被害の小さい場面に対して仕組みが大きいので、そぎ落としで外した（利用者の判断: 過剰な防御を減らす）。以前の版が作った venv に印のファイルが残っていても、何も起きない。見送った案: 印による自動の作り直しを残す（上の理由）、`pyvenv.cfg` の有無で判定して消す（レビューで、利用者の開発用 venv を、承認だけで中身ごと消すことが再現された）、既にある venv へそのまま pip install する（利用者の venv の中身を変える）。
  - 入れ先にシステムを選べるようにした理由: 利用者が「システムの Python に既にある環境に揃えたい」ことがあるため（利用者の要望）。`--system` は `pip install --quiet --require-hashes --user -r requirements.txt` で入れ、入れたあとにその Python から import できること（`systemUsable`）を確かめる。ユーザー領域は、システムの探索（①）が最初から見る場所なので、入れたあとは「システムにある」として扱われ、特別な経路は要らない。
  - 既定は venv（`--system` を付けたときだけシステム）。システムを変えない側を既定にするため。承認前の案内には、両方の入れ先と、システムの注意（他のツールの openpyxl と版が衝突しうる、アンインストールで消えない、仮想環境の Python では使えない）を書く。`--system` を指定しても、venv に固定版が既にあれば、何も入れずに成功し、「専用の venv に既にあるため、システムには何も入れていません」と伝える（`locate` の判定を変えない）。見送った案: `--system` のとき venv の判定を飛ばして必ず入れる（使える環境があるのに入れるため）、入れる前に `pip list --user` で既存の版を表示する（頼まれていない）。
  - 注意の文言: ユーザー領域に別の版の openpyxl が既にあれば、固定した版（3.1.5）に置き換わり、元の版には戻せない（レビューで指摘）。

## 算出の規則

### 優先順位（今日の優先）

対象は `Done`／`Cancelled` 以外で、前のタスクがすべて完了しているもの。点数の合計が高い順（実装は `core/schedule.js`）。

| 項目 | 点数 |
|---|---|
| 期限超過 | +100 |
| 期限点 | 残り 30 日以内は `(30 − 残り日数) × 1.5`（超過した分も加算）。残り 31 日以上は 0 |
| チェックリストの倍率 | 期限点に `1 + min(未チェックの項目数, 10) ÷ 10` をかける（最大 2.0）。`Waiting` は 1（かけない）。`+100` と重要度にはかけない |
| 重要度 | 高 +12 ／ それ以外 0（倍率のあとに足す） |

- 例（重要度なし）: 期限 5 日後・未チェック 3 件 ＝ 25×1.5×1.3 ＝ 48.75。期限 5 日後・項目なし ＝ 37.5。3 日超過・未チェック 10 件 ＝ 100＋49.5×2.0 ＝ 199。`Waiting`・期限 5 日後・未チェック 3 件 ＝ 37.5。期限 35 日後 ＝ 0。
- 以前あった「このタスクを前のタスクとする未完了タスク 1 件ごと +10」と「`Waiting` +15」は廃止した（設計判断を参照）。行の「理由」には、点数に使わなくなったあとも、「次のタスク N 件を止めている」と `Waiting` の催促・確認の文言を残す（`action: "chase"` も同じ）。点数は画面に出さない。
- 行の理由の「期限まで N日」は、期限点の範囲に合わせて、残り 30 日以内（以前は 14 日以内）に出す。
- 同点は期限の早い順、次に ID 順。丸めはしない。

### 日程変更

- 前のタスク（`predecessors`）をたどり、次のタスクを**最小限だけ**動かす。前のタスクの新しい期限を超えないようにするだけで、余裕のある次のタスクは動かない。
- `Done`／`Cancelled` は動かさない。依存が入力されていないタスクも動かない。
- 前倒しのときは、「詰める」を選ぶと、次のタスクも同じ日数だけ前倒しする（前のタスクの新しい期限より前にはしない）。
- この計算（`core/impact.js`）を使うのは、「Claude Code に依頼する」の反映だけ。画面の期限の変更は、前後を見ずにそのタスクだけを保存する（「ガントチャートとリスト」の節）。

### 状態と進捗

- タスクの状態は `To Do`／`In Progress`／`Waiting`（待ち先を持つ）／`Done`／`Cancelled`（進捗率の分母から除く）。
- プロジェクトの状態は `計画中`／`進行中`／`保留`／`完了`／`中止`。
- 遅延・リスクは状態ではなく自動判定のバッジ。「期限超過 N件」、「待ち長期化」（`Waiting` が `settings.waitingLongDays` 日以上）、「プロジェクト期限超過」。
- 進捗率は `Done` ÷（`Cancelled` を除く全タスク）。
- チェックリスト（`task.checklist = [{ id, text, done }]`）は、タスクの状態と連動しない。全項目をチェックしても状態は変わらず、進捗率にも使わない。状態を `Done` にするときだけ、未チェックの項目があれば警告する（「ガントチャートとリスト」の節）。

## 画面の動き

画面上部のナビは、ガントチャート・リスト・スケジュール・稼働・設定の 5 つ。`S.screen` が `gantt`・`list`・`schedule`・`workload`・`settings`（初期値は `gantt`）で、保存はしない。ガントチャートとリストは、同じ `renderProjects`（`opts.view`）で、絞り込み・「完了を隠す」の状態を共有する。画面内の「ガント／リスト」の切り替えボタンは持たない（`S.pview` は廃止）。

### 全体

- ヘッダー、ガントチャート・リストのフィルタの行、右側の列（今日のタスク・今日の優先）は、スクロールしても上端に固定する（CSS の `sticky`。ヘッダーの高さを `--hh`、フィルタ行の高さを `--th` に入れて、下の帯が、その下に付く）。固定表示は、画面のスクロールに対して、CSS の `position: sticky` で付ける（JS でずらさない。ずらすと、画面のスクロールが先に動き、日付が遅れて動いてから戻る）。新しい CSS は、`theme.css` の末尾の節にまとめ、すべて `#view` の中に限る。
  - **絞り込み行（`.ptool`）**: プロジェクトのチップは 1 行に収め、横にスクロールする（`.chips-row`。`flex-wrap:nowrap; overflow-x:auto`）。プロジェクト名のプルダウン（`data-projectpick`。完了も含む全プロジェクト）と「＋ プロジェクトを追加」は、スクロールの外（`.ptool-end`）で固定。チップは、状態が「完了」のプロジェクトを出さない（選択中のあいだだけ出す。完了のものは、プルダウンから選ぶ。「完了を隠す」ボタンの基準（全タスクが Done も含む）とは違い、プロジェクトの状態だけで決める）。大項目で絞り込む機能（`S.group`・`data-groupfilter`・`renderGantt`/`renderList` の `group` オプション・`groupNames`）は、利用者の希望でやめた（プルダウンに置き換えた）。各タスクの大項目・中項目の表示と編集は残る。プロジェクトが何件でも、固定の高さ（`--th`）は 49px のまま（30 プロジェクトで、折り返していたときは 231px。実測）。スクロールバーは出さない（`scrollbar-width:none`）。出すと、チップがあふれたとき、固定の行が 15px 高くなり、プロジェクトの数で高さが変わるため。代わりに、マウスの縦のホイールで横に動かし（`wheel`）、横スワイプ・Tab でも動く。デメリット: スクロールバーがないため、マウスだけの利用者は、ホイールを回すまで、あふれていることに気づきにくい。描き直しでは、チップの行の横位置を保ち、選択中のチップが見えなければ、行の中だけを動かす（`scrollIntoView` は、ページの縦も動かすので使わない）。
  - **ガント**: プロジェクトごとに、`section.pg` の中を、`.pgstick`（プロジェクトの見出し `.pg-head`。`sticky`、`top: --hh + --th + --gh`。`--gh` は操作の帯 `.gtop` の高さ）と、`.gwrap`（`.gstrip` + `.gscroll`）に分ける。`.gscroll` は横だけにスクロールする（`overflow-x:auto; overflow-y:hidden`）。`.gstrip` は、本物の日付軸（`.g-head .g-lane`）の写し（左の空き `.gsl` + 窓 `.gsv`）で、`sticky`（`top` に `--pgh`、見出しの高さ）。次のプロジェクトに入ると、見出しと複製が入れ替わる（`sticky` の動き。`section.pg` が範囲）。`data-todayfrac`・`data-s0`・`data-span` は、全プロジェクト共通の値を、各 `.gscroll` に付ける（ドラッグ・今日へ移動が `.gscroll` から読む）。
  - `.gwrap` は `padding-bottom: --sh + --sb`、`.gscroll` は同じ分の負の `margin-bottom`、`.gstrip` は `margin-bottom: -(--sh)`: 流れの高さを増やさず、`sticky` の範囲を複製の高さ（`--sh`）と横スクロールバーの高さ（`--sb`）だけ短くする。複製が、プロジェクトの下端（横スクロールバーを含む）を越えて、下のものに重ならない（`--sb` を除かなかったところ、複製の下端が表・枠の横スクロールバーの 15px に重なった。実測）。複製の目盛りの行は、本物の行の `column-gap`（12px）だけ右へ置く（測らないと、12px ずれた）。
  - 再描画（`render`）のとき、ガントの横位置（`scrollLeft`。全プロジェクトで同じ）とページの縦の位置（`scrollY`）を保つ。描き直しの間、`#view` に `min-height` を付けて、ページが縮んで `scrollY` が飛ぶのを防ぐ。`#view{overflow-anchor:none}`: 切らないと、ブラウザのスクロールアンカーが、描き直しのたびに縦の位置を +2px ずつずらした（実測）。`alignGScrolls` は、動かした枠の `scrollLeft` を他の枠にそろえる。代入で起きる `scroll` は無視する（`WeakMap` の `aligned`）。無視しないと、動いている最中の枠を、古い位置へ引き戻した（「今日へ移動」が 1px で止まった。実測）。「今日へ移動」のなめらかなスクロールは、先頭の枠だけに掛け、他の枠は `alignGScrolls` が追う。
  - **リスト**: プロジェクトの見出し全体は、`section.panel` の直下の `.pstick` にあり、`sticky`（ヘッダー・フィルタ行の下）。中身は、名前と状態の行 `.prow`（編集できる入力欄 `data-pf="name"`・`data-pf="status"`）と、その下の `.phead`（種別・開始・期限・進捗・稼働・注意の印）。利用者の希望で、注意の印（期限超過など）も固定する（印が折り返すと、固定の高さが増える）。未測定: 印が折り返したとき（3 行など）の高さ。画面の高さが低い（500px 前後）と、固定部分が増え、表の見える高さが減る（上限や折りたたみは足していない）。Tab で表の入力欄にフォーカスすると、固定部分の裏に隠れうる（`scroll-padding-top` がない。未実測）。列見出しは、表を包む `.twrap` の先頭の**複製**（`.thstrip`、`aria-hidden`。`renderList` が空で出し、`syncThStrips` が、本物の `thead` の各列の幅・余白・文字を測って写す）で固定する。`.thstrip` は `sticky`（`top: --hh + --th + --ph`。`--ph` は `.pstick` の高さで、`syncThStrips` が `section.panel` に入れる）。`.twrap` は表だけを含む（マイルストーン・履歴は外）。`padding-bottom: --sh + --sb` と、表の枠の負の `margin-bottom` で、`sticky` の範囲を短くし、複製が表の下端を越えない。固定していないときは、本物の `thead` に重なる（差 0px）ので、出し分けの JS（`thStripOn`・`updateThStrips`）は持たない。横スクロールの位置は、表の枠の `scroll` イベントで、複製の `translateX(-scrollLeft)` にそろえる（横方向だけ JS）。本物の `thead` が非表示（幅 860px 以下）のときは、複製を空にする（`:empty` で隠れる）。複製は、描き直し・画面の大きさの変更のたびに（`syncSticky` から）作り直す。リストの表は `pinTableHeads` の対象外。
  - 設定・稼働の表（`.tscroll` で `.tlist` でないもの）の列見出しは、従来どおり `pinTableHeads` がずらす。
- 右上の「ガント実績」のスイッチと、右の列の開け閉め（`showPrio`）は、このブラウザに保存する。右の列の開け閉めは、本体と右の列の境界線の取っ手（`.side-toggle`、`data-pref="prio"`）で行う。閉じても取っ手は残る。幅 900px 以下では、列が 1 つに回り込み、取っ手は横長の帯になる。取っ手の名前に「今日の優先」が入るので、パネルの有無は見出しの id（`h-rk`・`h-td`）で見る。
- URL に `?today=2026-10-20&time=10:15` を付けると、現在日時を固定して開ける（動作確認用）。

### ガントチャートとリスト

- ガントチャートは、土日・手動の休み（`settings.holidays`）・日本の祝日の列に、同じ着色（`.gwk`）を付ける。判定は `core/holidays.js` の `restDayChecker`。「土日祝を営業日に数える」の設定に関わらず着色する（日数の計算と作業枠にだけ効く設定のため）。営業日の指定（`workdays`）の日は着色しない。日表示（40 日以下の表示）のときだけ着色する（土日の着色と同じ）。
- 前のタスクの線は、編集画面のガントチャートだけに出す。`gantt.js` が、前のタスクのあるバーに `data-pre`（空白区切りの ID）を付け、`ui/deps.js` が、描画のあとにバーの位置を測って SVG（`.gdeps`）を重ねる。両端のバーが同じプロジェクトの表に出ているものだけ引く（「完了を隠す」で隠れた行・別のプロジェクトとの線は引かない）。バーのドラッグ中は、線がずれるので隠す。バーにマウスを置くと、`focusDeps` が、そのタスクを青、前のタスクを橙にし、つなぐ線を濃くし、ほかを薄くする。前のタスクも次のタスクもないバーは、自身だけを青にする（ほかは薄くしない）。
- 開始日（`taskStart`）は、`start` があればそれ、なければ前のタスクの期限の最大値、それもなければ期限。前のタスクがあるタスクにも左端のつまみを出し、ドラッグすると `start` に保存する（前のタスクの期限は見ない）。`start` を指定したタスクは、前のタスクの期限が動いても動かない。リストの開始日を空にすると、指定を外す（前のタスクから決まる日に戻る）。前のタスクを足しても、開始日は触らない（画面は `addPredecessor`。以前は外していたが、利用者が入れた開始日が黙って消えるため改めた。見送った案: 外したうえで通知する）。依頼で期限が指定した開始日より前になるときも、開始日を外して提案の注意に出す（外さないと保存の検査で失敗する）。前のタスクがあり `start` もあるデータは、`start` を使う。同梱のサンプルに該当はない（Excel 取り込みの結果は未確認）。
- 画面では、前後のタスクの確認をしない。期限・開始日の変更（リストの日付欄、ガントのドラッグ、編集の窓）は、そのタスクだけを保存する。次のタスクの期限を超えたときの警告、「前のタスクの期限より前にはできません」のエラー、日程変更の確認パネルは持たない。前後を見て動かすのは、「Claude Code に依頼する」の処理（`core/impact.js`）だけ。画面から期限を変えても、日程変更の履歴（`changeLog`）には残らない。
- バーにマウスを置くと（`focusDeps`）、そのタスクを青、前のタスクを橙、次のタスクを緑（`--next`）にし、前のタスクとの線を橙、次のタスクとの線を緑にする。ほかは薄くする。線の SVG は、前のタスクの ID を `data-from`、次のタスクの ID を `data-to` に持つ。
- 編集の窓（`views/taskpop.js`）は、ガントチャートでタスク名（`data-gedit`）またはバーをクリックすると開く。バーは、ドラッグせずに離したとき（`app.js` の mouseup で `dd` が 0）だけ開く。窓は `S.tpop`（`{ id, x, y }`、メモリのみ）で持ち、`fixed` で、クリックした位置の近くに置く（`placeTaskPop` が画面の端と下端の帯を避ける）。入力は、リストと同じ `data-f`・`data-id` を使うので、保存はリストの処理が受け持つ。状態の欄（待ち先・Done の確認を含む）と前のタスクの欄は、リストと共用（`statusCellHtml`・`predEditHtml`）。窓の外のクリック・Esc・タブの切り替え・ファイルの読み直しで閉じる。タスク名のクリックは、以前はリストへ移っていた。その動きは窓の「リストで開く」に移した。
- 取っ手の矢印の向き（`‹ ›`）は、900px 以下の横長の帯でも変えない（未確認の見た目: 向きが横を向いたまま）。
- ガント・リストは、(大項目 ▸ 中項目) ごとに区切り行を出す。並びは、大項目の登場順、その中は中項目の登場順で、未設定は末尾の「（なし）」。並べ替えは、ドラッグで行う（次の項目）。見出しの呼び名は `settings.labels` で変える。
- タスクの並べ替え: リスト行の ID 欄とガントのラベルにある「⠿」（`data-mvh`）をドラッグする（ブラウザ標準のドラッグ。スケジュール画面と同じ）。落とし先は、タスク行（上半分はその行の前、下半分はその次。`data-mvrow`）と見出し行（そのセクションの先頭。`data-mvgrp`・`data-mvg`・`data-mvsg`）。`app.js` の `planOrder` が、`edit.js` の `moveTask(data, id, { beforeId, group, subgroup })` への指定を決める。
  - `beforeId` があればその前に入り、そのタスクの大項目・中項目になる。`null` なら、指定した大項目・中項目（空は「（なし）」）の末尾に入る。同じプロジェクトのタスクだけを指せる（別のプロジェクトは例外）。動かしても今の表示と変わらないときは、同じデータを返し、落とし先にしない。
  - 動かしたあと、そのプロジェクトのタスクを、動かす前の表示順（セクション順）のとおりに並べ直して、配列の同じ位置へ戻す（他のプロジェクトのタスクの位置は変わらない）。`groupSections` が大項目を最初の登場順で並べるので、配列の順を表示の順に揃えておかないと、セクションの順がずれるため。したがって、並べ替えたプロジェクトの保存ファイルの並びは変わる。
  - 見送った案: 大項目の見出しごとの並べ替え（次の段階）。別のプロジェクトへの移動、「Claude Code に依頼する」からの並べ替え、キーボードだけの操作。WBS の再取り込みは順を変えない（新しいタスクは配列の末尾に足され、表示ではそのセクションの末尾に出る）。
  - 動作確認: リストとガントのドラッグ（行の前、見出しの先頭、別セクションへの付け替え）を、実ブラウザ（Chromium、Playwright）で確認した。タッチ操作は未確認（ブラウザ標準のドラッグはタッチに対応しないことが多い）。
- ガントのバーは、開始日のマスから期限日のマスの右端まで（期限の日を含む）。幅は `(期限 − 開始 + 1) / 全体の日数`。プロジェクト全体のバーと実績のバーも同じ。期限の表示（`g-due`）は、バーの右（期限の翌日の左端）に付ける。マイルストーンは、その日の左端に置く。期限の表示は、点でも、期限の翌日の左端に付ける。ドラッグ中のバーの幅（`app.js`）も同じ式。
- 重要度は、ガントのタスク行のラベルに出す（`gantt.js` の `imp-high`、`theme.css`）。高は左端に太い赤（5px）の縦線と、行全体の薄い赤（`--bad-soft`）の背景。低・未設定と、完了（`Done`・`Cancelled`）したタスクには付けない（「今日の優先」も完了を除くため）。縦線は横スクロールで流れないよう固定のラベル（`.g-label`）に付け、行の背景は `:has()` で塗る（行のタグの文字列に依存するテストがあるため、行に class を足さない）。凡例に 1 項目を足した。案は 4 案から選んだ（見送った案: 「中」の細い縦線（重要度を高／なしの 2 値にしたため廃止）・「高」の印・今日の優先の順位・見出しの件数と絞り込み・バーの輪郭。必要になれば足す）。
- 点（`dot`）は、開始（`start`）も前のタスクもない、期限だけのタスクに限る（`ganttRows` の `point`）。日付のマスの中央に置く（`left` は「期限の日の左端 + 半マス」。`.g-lane .mk` は `position:absolute`）。開始を指定したタスクと前のタスクのあるタスクは、開始 ≥ 期限でも、期限の日 1 日分の棒にする。1 日分の棒も、両端のつまみで開始と期限を別々に動かせる（右つまみが開始より前へ動かないのは、開始の指定がない開始 ≥ 期限のタスクを除く）。以前は、開始 ≥ 期限をすべて点にしていて、`.g-lane .mk` に `position:absolute` が無く、点が範囲の先頭日（x=0）に出ていた。以前は幅が「期限 − 開始」で、期限の日のマスに届かなかった。
- マイルストーンのラベルは、重ならない最初の段（1 段 18px）に置く。段は `assignLevels`（`gantt.js`）が決める。描いたときは、画面幅を 1000px と仮定した見積もりで決める。画面では、描いたあと、ウィンドウの幅を変えたときにも、`layoutMilestones` がラベルの実際の幅を測って段と行の高さを決め直す（`drawAllDeps` から呼ぶ）。見積もりだけだと、600px の画面で重なった。ウィンドウ幅を変えてから決め直すまで、0.4〜0.5 秒かかることがある（原因は未確認。自動操作ツールの幅変更の遅れの可能性がある）。
- ガントの「完了を隠す」は、Done のタスクの行に加えて、複数のプロジェクトを出しているときは、完了したプロジェクト（状態が「完了」、またはタスクが全部 Done）も隠す。1 つを選んでいるときは隠さない。

- **チェックリスト**（実装は `core/checklist.js`、編集欄は `views/checklist.js`、編集関数は `edit.js`）。
  - ガント: 項目のあるタスクの行で、左のラベルのタスク名の下に細い線（済みの割合）と「M/N」を出し（`checkMeterHtml`）、バーは左端から M/N に比例した幅を濃く塗る（`.gck`）。バーの右には数字を出さない。`Done`・`Cancelled` のバーには塗りを付けず、点（期限だけのタスク）は塗りなしでラベルだけ出す。全項目が済みのとき、線と数字は緑。項目のないタスクの表示は変わらない。
  - リスト: 「チェック」列に「▸ M/N」（項目なしは「＋ 追加」）。押すと、その行の直後に編集欄の行（`.ck-tr`）が開く。開いているタスクは `S.checkOpen`（メモリのみ、保存しない。ファイルを読み直すと閉じる）。
  - ガントの編集の窓: 「期限」の下・「前のタスク」の上に、同じ編集欄を常に出す。
  - 編集欄: 項目ごとに取っ手（⠿）・チェック・文言・削除、末尾に追加欄。追加は Enter（日本語入力の変換確定の Enter、`isComposing` では追加しない）。文言の編集は `change`（Enter かフォーカスが外れたとき）で保存し、1 文字ごとには保存しない。空にすると「項目を入力してください」で元に戻る。チェック・追加・削除・並び替えは操作のたびに保存する。並び替えは取っ手のドラッグ（同じタスクの中だけ）。項目の `id` は `c<最大番号 + 1>`（削除した番号が末尾なら再利用されうるが、同時に存在する `id` は重複しない。保存の競合で当て直しても結果が同じ）。
  - `Done` にするときの警告（`donecheck.js` の `planDone`、`S.pendingDone` の `stage`）: 未チェックの項目があれば、先にチェックの警告（残りをすべてチェックして Done／未完了のまま Done／やめる）を出し、続けて未来の予定枠の確認（あれば）を出す。どの段階の「やめる」も、状態も項目も変えない。`Cancelled` など `Done` 以外への変更では、チェックの警告は出ない。リストの選択・ガントの窓・今日のタスクの「完了」ボタンは、どれも `changeStatus` を通る。今日のタスクに入っているタスクは、警告が右の列の行に出る（予定枠の確認と同じ）。依頼（inbox）の状態変更は警告しない（変更案を見て承認する流れが確認にあたる）。

  - 確認したこと（Chromium・Playwright。ファイル選択は `showOpenFilePicker` を差し替えて開いた）: リストの展開・Enter での追加・変換確定の Enter（`isComposing` を立てた `KeyboardEvent`）で増えないこと・チェック・文言の変更・空文言の差し戻し・削除・ドラッグでの並び替え（合成した `DragEvent`）・ガントの窓との同期。`Done` の警告（リストの選択・今日のタスクのボタン・ガントの窓）の 3 つの選択肢と、チェック → 予定枠の順、どの段の「やめる」も不変であること。画面案（Artifact のボード 1〜4）との見比べ（ガントのラベルの線と M/N・バーの塗り・窓の欄の位置・リストの展開・警告の枠・今日の優先の行）。`inbox` は CLI で `propose` → `approve` まで（`tests/inbox-cli.test.js`）、提案のあとに項目が増えると `approve` が失敗すること。
  - 未確認: 実際の日本語入力（IME）での Enter、実際のマウスでのドラッグ、タッチ操作、幅 600px 以下の画面、項目が多いときの縦の長さ、ラベルが約 4px 高くなったときの固定表示の高さ、自動の読み直し（4〜16 秒ごと）で入力途中の文字が消えるか、`Waiting` の `+15` と次のタスクの `+10` を廃止したあとの実データでの順位の使い心地。

### 今日のタスクとスケジュール

- 「今日の優先」と「今日のタスク」の行には、チェックリストのあるタスクに細い線と「M/N（残り K 件）」を出す（今日のタスクの完了済み・取り消し済みの行には出さない）。
- 「今日のタスク」は、`views/prio.js` の `renderTodayTasks` が、今日の日付に作業枠があるタスクを枠から導く（保存しない）。ガントチャート・リスト・スケジュール画面の右の列（`renderSide`。`showPrio` に従う）で、「今日の優先」の上に出る。
  - 行に状態の pill と、「着手」（To Do・Waiting のとき。In Progress にする）・「完了」（Done・Cancelled 以外。Done にする）のボタンがある。
  - Done・Cancelled は薄く、ボタン無しで末尾に出る。
  - 今日のタスクに入ったタスクは、`renderPrio` が一覧から除く（`rankTasks` は変えない）。
  - ボタンは、リストの状態の select と同じ関数（`app.js` の `changeStatus`）を通る。
  - 日表示の作業枠は、ボタンの代わりにタスクの状態の文字を出す。
- まだ開始していない予定枠があるときの確認（`doneAskHtml`）は、対象が今日のタスクにいればパネルの行に、いなければ（リストの select から）リストの行に出る。解除されるのは開始前の予定枠だけ（`futurePlanned`）。進行中の枠は残り、終わったあとに実績にできる。
- 枠・会議のドラッグと下端ドラッグの間、`app.js` の `showTip` がポインタの近くに「開始–終了」を出す（`hideTip` が drop・dragend・離したとき・描き直しで消す）。週表示のブロックも開始–終了を出す。
- スケジュールの枠は、予定（青緑）・実績（緑）・未確認（橙の点線）。会議は紫。枠は実績時間の記録だけで、タスクの状態は変えない。
- 「置ける日」は、`core/holidays.js` の `offDayChecker(settings)` で決める。土日・`holidays`・`nationalHolidays` の日は休み、`workdays` の日は休みでない。`settings.countWeekendsAndHolidays` が `true` のときは、土日と `nationalHolidays` を休みにせず、`holidays` だけを休みにする（`sessions.js` のエラー文は、このときは土曜の手動の休みも「休みの日」と言う）。
  - 休みの日は、`freeOf` が空き時間を出さず（週表示の列は `weekend` 扱いで「—」）、`sessions.js` の `check`（`addSession`・`moveSession`・`resizeSession`）が「置けません」を返す。
  - すでに休みの日にある枠はそのまま残り、同じ日の中なら伸縮・移動もできる（`check` の `ignoreId`。新しく置く・別の日から動かすときだけ止める）。

### 会議と稼働

- 予定表から取得した会議は、「参加しない」とプロジェクトだけ変更できる。
- 「参加しない」の会議（`skip: true`）は、スケジュール画面の右上の「参加しない会議」ボタンで、カレンダーに出す・隠すを切り替える。初めは隠す。隠すと、週・日の両方で描かず（選択中の会議だけは出す）、凡例の「参加しない会議」も出さない。空き時間・稼働の計算とデータは、出す・隠すで変わらない（どちらでも、空き時間として扱う）。状態は `S.prefs.showSkipped`（`prefs.js`）に持ち、`localStorage`（`project-board.prefs`）に保存する。`data.json` には保存しない。
- 会議のプロジェクトは、規則（件名のキーワード → プロジェクト）で自動に付き（`projectBy` が `rule`）、手動で付けたもの（`manual`）は規則を変えても動かない。
- 稼働は、プロジェクト別のタスクの時間（実績の作業枠）と会議の時間（確認済みで、参加するもの）を集計する。プロジェクト未設定の会議は「プロジェクト未設定の会議」にまとめる。未確認の枠・会議は含まない。

### 設定タブ

- **節の構成と折りたたみ**: 節は 4 つ（基本の設定・休みと営業日・キーワード規則・WBS の取り込み記録）。「休みと営業日」の中に小見出しが 3 つ（日本の祝日・休み（手動）・営業日として扱う日）ある。7 つとも `<details>` で、見出しを押すと開閉する。
  - 開閉は `S.settingsClosed`（閉じている節の ID の配列。ID は `prefs.js` の `SETTINGS_FOLDS`）に持ち、`localStorage`（`project-board.settingsClosed`）に保存する。保存が無い・壊れている・使えないときは、すべて開く。`data.json` には保存しない（ブラウザごとの好みのため）。
  - `app.js` が `toggle` イベントをキャプチャで受けて記録する（`toggle` はバブリングしない）。開閉では描き直さない。描き直したときは、`renderSettings` の `opts.closed` から開閉を復元する。
  - 閉じた節の中の入力と `validate` の注意も、HTML には描く（見えないだけ）。閉じた節の見出しには「注意 N 件」を出す（`fold` の第 6 引数。親の「休みと営業日」は 3 つの小見出しの合計、「キーワード規則」は `ruleError` の有無で 1 件）。画面上部のバナーにも、`validate` の注意は元から出る。
  - 動作確認: 描画と保存は `npm test`。実ブラウザ（Chromium、Playwright）で、クリックとキーボード（Enter）での開閉、保存、再描画後と再読み込み後の復元、注意の件数の表示を確認した。描画時に `open` の節で `toggle` が発火するが、記録は変わらない。スクリーンリーダーでの読み上げは未確認（Chromium のアクセシビリティツリーでは、見出しは heading として出る）。
- **基本の設定**: 営業日の数え方・勤務時間・待ち長期化の日数・見出しの呼び名を、その場で保存する（`updateSettings`）。
  - 勤務時間は開始・終了を組で保存する。`type="time"` は時・分を打つたびに change が起きるので、打ち終わる（0.8 秒止まる）か入力欄を離れてから保存する（`changeSettingSoon`）。
  - 保存に成功したら描き直さない（描き直すと入力の位置が「時」に戻る）。
  - 不正な値は、先に検査して通知し、入力欄だけを保存された値（形が違えば既定値）に戻す（`restoreSettingInputs`。描き直すとフォーカスが消えるため）。
  - 形が違う値は `validate` が注意（warning）にし、設定タブは既定値を入力欄に出して横に注意を出す。読む側に fallback は無く、勤務時間が `HH:MM` でないとスケジュール画面は動かない。
- **キーワード規則**: ↑↓で並べ替えられる（`moveProjectRule`）。上の規則が先に当たるので、並べ替えたら会議へ付け直す。
- **営業日の数え方**: 「基本の設定」の表の先頭の行。チェックボックス `data-set="countWeekendsAndHolidays"` が `settings.countWeekendsAndHolidays` を保存する（`updateSettings`。`false` ではキーを消す）。他の入力と違い、保存後に描き直す（「日本の祝日」「休み（手動）」の小見出しの説明を切り替えるため）。`true` 以外（`"true"` など）はオフとして描き、`validate` の注意をその行に出す。
  - オンのとき、`calendarOf` は `off` を手動の休みだけにして `countWeekends: true` を足し、`dueAfter` は土日を飛ばさない。`holidayRangeDays` は期間の全日を返す（除外は 0）。祝日の自動取得（`needsHolidayUpdate`、`propose` の取得と範囲の注意）は行わない。保存済みの `nationalHolidays` は消さないので、オフに戻すと再び使う。
  - ガントの土日の色分け（`metrics.js` の `timeTicks`）は、曜日の表示であり営業日の計算ではないので、オンでも変えない。
  - 実機（Playwright）での確認は未確認。
- **日本の祝日・休み・営業日**: 「休みと営業日」の節の中の 3 つの小見出し。`validate` は 3 つの形が違うとき注意（warning）にし、画面は壊れた値を空として描いて小見出しの下に注意を出す。
  - 「日本の祝日」: `settings.nationalHolidays`。読み取り専用。取得は `tools/holidays.js`（営業日を使う提案では `tools/inbox.js propose` も必要なら取得する。「日本の祝日の取得」を参照）。

  - 「営業日として扱う日」: `settings.workdays`。`addWorkday`・`removeWorkday`。

### 保存と競合

- CLI の保存（`tools/cli.js` の `save`）は、`readJson` で読んだ時点のファイルの印（更新日時とサイズ）を覚え、書く直前に比べる。違えば「他で更新されました」で止まる（もう一度読み直して実行する）。見張りの印を書く `wait` は、止まったら次の回に書く。確認から置き換えまでの数ミリ秒の隙間は残る（ロックは作らない）。置き換えが 3 回失敗したときは、上書きせず例外にする。

- 保存と読み直しの順序づけは `ui/sync.js`（`createSync`）。画面の編集を 1 本の列に並べて保存し、競合したら最新のファイルに同じ編集を当て直す。Claude Code の更新の読み直し（`pollInbox`）も同じ列に並べる。
- 当て直しの保存が失敗したとき（書き込みの権限・I/O のエラー）は、読み込み時点（`loadedAt`）を元に戻す。進めたままだと、次の保存が競合を検出せず、画面の古いデータで他の更新を上書きする。
- 当て直せなかったとき（同じ依頼がすでに処理されていた、など）だけ、保存時に「他で更新されました。再読込してください」と出る（上書きはしない）。読み直すと、画面の保存できていない変更は消える。
- 見送ったこと（既知の穴）: 保存の確認と書き込みの間の競合。CLI（`save`）も画面（`store.js` の `save`）も、「更新日時を見る → 書く」の 2 段階で、プロセスをまたぐロックはない。確認と書き込みの間（数ミリ秒）に相手が書くと、その編集は検出されず消える。起きうる組み合わせは、見張り（`wait`）の見ている印（30 秒ごとに全体を書き直す）と、画面での編集が、同じ数ミリ秒に重なるとき。消えるのは直前の 1 回の編集で、画面なら再読み込みの後に気づく。ロックファイルは、1 人で使う規模には過剰なので入れない。確認していないこと: 実際に編集が消えるかを、2 つのプロセスで同時に書いて試していない（未確認）。
- 直接保存に対応しないブラウザでは、読み込みだけできる。変更は「JSON を書き出す」で保存する。
- 画面は、ファイルを自動で読み直す（保存できる環境のとき）。帯が開いている間や依頼の処理中は 4 秒、そうでなければ 16 秒ごと。
- 前回のファイルの記憶は、Edge で `file://` から開いて効くことを確認した。権限の確認の文言は Edge のバージョンで違う想定で、実際の文言と「何も押さずに開く」動きは未確認。

## 取り込み（intake）

WBS と規則は「読み取り → 変更案の表 → 利用者の承認 → 書き込み」の順で、承認の前はタスクを変えない。予定表の会議は、承認の確認なしで書く（後述）。

- **文章（メール・議事録・メモ）**: `intake` ではなく、HTML の依頼で行う（`inbox` エージェントが、本文から `addTask`・`moveDue` の提案を作る）。次の 2 項目は、その手順の規則。
  - 期限が書かれていないタスクは、Claude が前のタスクと `businessDays` で仮に置き、日付の足し算は `propose` が行う。行番号で直して再提案し、承認後に登録する。
  - 重要度・待ち先（状態）は、依頼では受けないので入れない（画面で設定する）。
- **WBS**: 列の対応と変更案を一緒に見せて承認を 1 回にする（承認後に `mapping-set` → `wbs-apply`）。ガントチャート・リストの変更履歴は、`source` があり日数が 0 の記録を出さない。
- **予定表**: 取り込みの結果に、使った MCP 名を出す。`/project-board:intake calendar` は、変更案の表も承認の確認もなしで、`calendar-auto` を実行して書く（見張りからの呼び出しと同じ手順）。確認済みの実績を承認なしで消さないため。
  - 承認を外した理由: 承認なしで `calendar-apply`（`syncMcpEvents`）を使うと、予定表から消えた・対象外になった確認済みの会議（実績）が消える。実績を残す動きは `calendar-auto` にあるので、そちらに揃えた。
  - 自分だけ・自分と会議室だけの予定は、取り込まない（`import/calendar.js` の `excludeSolo`。純関数で、`planCalendarSync` が `syncMcpEvents` の前に呼ぶ）。取得した予定の `attendees`（`[{type: "person"|"resource", email, name}]`）から判定する。
    - 自分 = `email` が `selfEmails` のどれかと一致、または `name` が `selfNames` のどれかと一致（どちらも、前後の空白と大文字小文字を区別しない完全一致）。会議室 = `type` が `resource`、または `name` が `roomKeywords`（既定は「会議室」）を含む。自分と会議室を除いた参加者が 0 人なら対象外。
    - `attendees` の項目がない予定は、参加者が不明なので、取り込む。空の配列は「参加者なし」として対象外にする。MCP が参加者を返さないときに、エージェントが空の配列を書かないよう、`agents/intake.md` に書いてある。
    - `attendees` の要素が `null`・文字列など、形が崩れている予定も、不明として取り込む（例外にしない）。
    - `selfEmails` も `selfNames` も未設定なら、自分を特定できないので、何も除かない（参加者つきの予定があれば `warnings` に出す）。どちらかを設定済みでも、どの予定にも `attendees` がないときは、判定できていないと `warnings` に出す（MCP が参加者を返さないと、機能が黙って効かなくなるため）。
    - 設定は `project-board-mcp.json` の `calendar` の任意の項目 `selfEmails`・`selfNames`・`roomKeywords`（空でない文字列の配列）。`tools/intake.js calendar-plan|calendar-apply|calendar-auto` が、置き場（`PROJECT_BOARD_HOME` か `--data`）から読む。判定を LLM に任せず、CLI で行うため。`schema_version` は上げない（任意の項目の追加。既存のファイルはそのまま読める）。
    - `/project-board:mcp` は、`selfEmails` か `selfNames` が保存済みなら、手順 4 で聞かずに保存済みの値を伝える（変えたいと言われたときだけ聞き直す）。名前は完全一致なので、手順 5 の試し取得で、取れた参加者の表示名を見せ、保存した名前と同じものがあるかを利用者に確かめてもらう（一致しないと警告なしで除外されないため）。同じものがない・確かめられないときは、手順 4 に戻って入れ直すかを聞く。`selfEmails` だけが保存済みの人には、保存済みの値を伝えるときに「名前も保存できる」と一言添える（聞くかどうかの条件は「どちらかが保存済みなら聞かない」のまま。両方が保存済みのときだけ聞かない形にすると、名前を使わない人に毎回聞くことになるため）。同じ表示名の別人がいると、その人を自分とみなすため、心当たりがないかも確かめる。カンマを含む表示名（「Yamada, Taro」など）は、保存の区切りと同じなので、保存できない（メールアドレスだけにする。エスケープには対応しない。名前にカンマがある人は少ないと見て、見送った）。入れ直すときは、手順 4 の「保存済みなら聞かない」にかかわらず、名前を聞き直す。
    - `mcpconf.js set` は、保存済みの値に合成する（`set calendar selfEmails=…` だけで足せる）。不明な項目（打ち間違い）は例外にする（黙って無視すると、除外されないことに気づけないため）。以前は、必須の 2 項目を毎回指定する形だった。
    - 取り込み済みの会議が対象外になると、次の取り込みで `removed`（削除）に出る。終わった会議と `confirmed: true`（稼働の実績に数えている）のものは、`calendar-auto` が残す（`held`）。`calendar-plan` の出力は `{added, updated, removed, excluded, removedByExclusion, warnings}`（`removedByExclusion` は、対象外になって消える取り込み済みの会議 `{id, title, date, confirmed}`。確認済みの実績が消えることを、エージェントの文章に頼らず、出力で見せるため。`excluded` は `{externalId, title, date, start, end}` だけ。参加者のメールアドレスを、エージェントの文脈に出さないため）、`calendar-apply` の `summary` に `excluded`（件数）が付く。設定ファイル（`project-board-mcp.json`）の指定が正しくない（`selfEmails` が文字列、など）ときは、`validateMcpConfig` の理由を出して止まる（以前は、設定を読まずに動いていた）。エージェントは、取り込みの後に、参加者のメールアドレスを含む `fetched.json` を消す。
    - 名前のキーワード（`roomKeywords`）は、`type` に関係なく、人の名前にも部分一致する（`resource` 種別を返さない MCP でも、会議室を判定できるように、承認済みの仕様とした）。キーワードに短い言葉を足すと、人の名前に当たって、本物の会議を除外しうる。除外は、新しい予定では件数にしか出ない。取り込み済みの会議が除外されたときだけ、削除の行に件名が出る（`calendar-auto` では、終わった会議・確認済みの会議は残る。消えるのは、これからの未確認の会議）。
    - 見送った案: 辞退した予定の除外、手入力の会議の除外、定期的な予定のシリーズ単位の判定。
  - **自動更新（`calendar`。見張りからの呼び出しは `calendar（見張りから）`）**: `/project-board:watch` が、見張りの開始時と 30 分ごとの再起動時に、`project-board:intake-calendar` エージェントへ頼む（手順 1.5。Monitor を起動した後に行う。MCP ツールの許可確認が出ても、依頼の見張りの開始が止まらないように）。承認の確認なしで `tools/intake.js calendar-auto` を実行して書く。見張り中は端末で止まれないため。
    - エージェントは**バックグラウンドで**頼む（前景で呼ぶと、更新の間と、許可の確認で待つ間、見張りの依頼の処理が止まるため）。エージェントの報告は、`blocked`・`warnings`・`held` を含めて、そのまま利用者に伝える（サブエージェントの報告は、利用者の画面に出ないため）。`blocked` の理由には、次の行動（`/project-board:mcp`、`/project-board:intake calendar`）を書く。全件が対象外のときの停止は、休暇などで 14 日分が本当に空になった場合も止める。手動の `calendar` は、`blocked` のときだけ、`calendar-plan` で消える会議（件名・日付）を見せて、削除してよいかを利用者に聞き、「はい」のときに `calendar-apply` を実行する（終わった会議・確認済みの会議も消えると添える）。見張りからのときは聞かない。
    - 純関数 `planAutoSync`（`import/calendar.js`）が、`planCalendarSync` の結果から、終わった会議（`meetingPast`）と確認済みの会議の、更新と削除を取り除く（`held` に出す）。実績になる記録を、予定表での変更や取得の不具合で失わないため。予定表から消えた会議は、終わっていなければ（進行中・これから）削除する。ただし「参加しない」の会議は、取得に無いだけなら残す（利用者の印を、取得の欠けや externalId の変化で失わないため）。取り込みの対象外（自分だけの予定）になった会議は、「参加しない」でも消す。
    - 取得が 0 件、または全件が対象外になって、削除の対象があるときは、削除しない（`blocked` に理由を出す）。MCP が取得に失敗して空を返しても、自分のメールアドレスの設定が誤っていても、会議を全部消さないため。取得の失敗（ツールが使えない・エラー・結果が切り詰められた）は、エージェントがコマンドを実行せず、1 行で知らせる。`fetched.json`（メールアドレスを含む）は、成功しても失敗しても消す。
    - 守っていないこと（受け入れた）: 取得が一部だけのとき（件数が 1 件以上）、書かれなかった未確認の会議は削除される（エージェントの指示で防ぐだけで、コードの閾値はない）。MCP が日時のタイムゾーンをずらして返すと、未確認の会議の日時が、そのまま上書きされる。保存の競合は、既存の `save` と同じ（ロックなし。CLI は `readJson` で読んでから書くまでに他が書き換えていれば、書かずに例外にする。HTML は画面の競合の扱いに従う）。
    - 範囲は今日から 14 日後まで。範囲の外と手入力の会議は変わらない。「自分だけの予定を除く」設定も効く。
    - `calendar-auto` の出力は `{ok, summary: {added, updated, removed, excluded, held}, held, blocked, warnings}`。`held` は `{id, title, date, change: "updated"|"removed"}`。時刻は `nowLocal()`（実行時の現在）で判定する。
    - 見送った案: 終わった会議も、予定表から消えたら削除する（稼働の実績を失うため）。更新を見張りの開始時だけにする（見張りが長く続くと、予定表が古くなる）。HTML の「更新」ボタン。
    - 未確認: 実際の予定表 MCP での動作。見張りの開始時に、予定表の MCP ツールの許可確認が出て、止まるかは未確認（出た場合は、一度許可すれば、以降は止まらない想定）。実際の予定表 MCP での動作は未確認（参加者の返り方は MCP ごとに違う）。

### Excel の WBS

- 列の意味（大項目・中項目・件名・期限・前のタスクなど）は Claude が見出しと内容から判断し、対応表を見せて確認を取る。承認された対応表はプロジェクトごとに保存する（`settings.wbsMappings`）。
- 階層は、列・結合セル・インデント・番号のどれで表されていても読める。末尾の行（子を持たない行）をタスク（小項目）にし、その上の 2 段を大項目・中項目にする。
- 再取り込みでは、`wbsKey`（大項目/中項目/件名の連結）で同じタスクを探し、期限などを更新する。
  - `wbsKey` を持たない手入力のタスクは、同じ件名のものが 1 つだけなら同じタスクとして扱い、取り込みで `wbsKey` を付ける（重複して追加しない）。
  - 画面で直した件名は上書きしない。
  - WBS に無くなった既存のタスクは削除せず、一覧で知らせる。
- Python 3.8 以上と pip が要る。システムの Python に使える openpyxl があれば、何も入れずにそれを使う。無ければ、初回だけ、プラグイン専用のフォルダの `venv` を作り、その中に `openpyxl` と依存の `et_xmlfile`、`defusedxml` を入れる（`--system` なら、システムの Python のユーザー領域。ネットワークが必要。約 20 MB、約 10 秒）。承認なしには入れない。
- `tools/xlsx_dump.py` が読む範囲は、1 シートにつき 5000 行 × 200 列まで（出力は最大 2000 行。範囲がそれより広いシートは `truncated: true`）。遠い隅にセルが 1 つあるだけで範囲が `A1:XFD1048576` まで広がり、全部を読もうとして終わらなくなるため（`tests/fixtures/wbs-stray-cell.xlsx` で再現。修正前は 20 秒で打ち切るまで止まっていた）。
- `tools/xlsx_dump.py` は、展開後の合計サイズが 300MB を超える xlsx を、読む前に断る（openpyxl は範囲を絞る前にシート全体をメモリへ読むため）。`read_only` での読み込みは見送った: 結合セルの展開と非表示の行・列の判定に、通常モードの `merged_cells`・`row_dimensions` が要る。
- WBS の取り込み（`import/wbs.js`）は、開始日が期限より後になる行（行の値、または既存タスクの値との組み合わせ）を `rejected` に入れる。通すと、新規ではガントの行が逆になり、更新では `updateTask` が例外を投げて取り込み全体が止まるため。
- `tools/xlsx.js` のサブコマンド:
  - `doctor`: 診断のみ。何も変更せず、使う Python のパスと、openpyxl の場所（システムか専用の venv か）を表示する。
  - `setup`: `--yes` なしは入れ先（専用の venv・システム）と内容を表示して終了コード 3、`--yes` で入れる（既定は venv、`--system` を足すとシステムのユーザー領域）。知らない引数（旧 `--into` を含む）は、使い方を出して終了コード 2。
- `tools/xlsx.js` の終了コード: 0 成功、1 実行時のエラー、2 引数・設定のエラー（置き場が決まらないなど）、3 読み取りの環境が使えない（システムにも専用の venv にも無い・版のずれ・壊れている・承認待ち・Python が無い）。3 のときは、利用者に入れ先を確認して `setup --yes`（システムは `--system --yes`）を実行する。
- 置き場の優先順: 環境変数 `PROJECT_BOARD_HOME` → 引数（`--data "${CLAUDE_PLUGIN_DATA}"`）→ なければ終了コード 2。`tools/mcpconf.js` も同じ。

## HTML からの依頼（inbox）

### 動き

- 処理待ち（`pending`）・処理中（`working`）の依頼にも、画面に「却下する」を出す。見張りが止まる、受け取った後にセッションが落ちるなどで、`wait` が知らせない依頼（`working`）は、誰も処理しない。画面から取り下げられるようにした。見送った案: `wait` が受け取って長く経った `working` を再通知する（`submit --working` の依頼と区別する材料が要る）。

- 画面の下端の帯「Claude Code に依頼する」から、日程の見直し（`moveDue`）・タスクの登録（`addTask`）・メール、議事録、メモからの取り込み（この 2 つの操作に分ける）を依頼する。依頼は `data.json` の `inbox` に書かれ、見張っている Claude Code が提案（変更案）を作る。承認するまで、タスクの日程・前のタスク・一覧は変わらない。
- 依頼で受ける操作は `addTask` と `moveDue` の 2 種類だけ（`core/schema.js` の `PROPOSE_OPS`）。状態・重要度の変更、削除、プロジェクトの追加と変更、マイルストーン、チェックリストの項目の変更、前のタスクの付け外しは、画面で行う。`inbox` エージェントは、そのような依頼に、`ask` で「この依頼は画面で行ってください」と返し、提案を作らない。
- できないこと: 会議の追加・削除。Excel の WBS・予定表・会議の規則の取り込みは `/project-board:intake`。
- 履歴は最新の 20 件まで（処理中のものは消えない）。1 件の文章は 4000 文字まで（やりとりの件数の上限は無い。「設計判断」を参照）。
- 変更履歴には、期限を動かす操作ごとに 1 件（日数・理由つき）と、登録があるときの 1 件（`source` が `inbox`。画面の「日程変更の履歴」には出ない）が残る。登録の 1 件の `reason` は「受信箱: 登録 N 件・期限の変更 N 件」の形（要約も同じ形）。

### 反映の規則

- 操作は、`addTask`→`moveDue` の順に当てる（それぞれ書かれた順）。`addTask` の前のタスクは、全部足してから結ぶ。前のタスクを足したとき、次のタスクの期限が前のタスクより前なら、前のタスクの期限と同じ日まで動かす。
- `addTask` には、文字列の配列 `checklist`（空文字は除く）を付けられ、反映するときに `c1` から採番する。`predecessors` と `moveDue` の `taskId` には、同じ依頼の `addTask` の `ref` を書ける。
- 承認時の `stale` の判定は 1 つ: いまのデータで操作をもう一度計算し（`simulate`）、変更案の表の同一性（`sectionsKey`。期限の行は ID・旧い期限・新しい期限、登録の行は `ref`・件名・プロジェクト・大項目・中項目・期限・前のタスク・項目の文言。開始日の既定と理由の文は含めない）が提案と違う、または計算できない（タスクやプロジェクトが消えた、完了した、など）ときは `stale`。以前の `base`（触るタスクの値）との二重の比較はやめた（表の比較で足りる）。保存済みの提案に `base` が残っていても、読まない。
- 保存済みの提案の `ops` に、`PROPOSE_OPS` 以外の操作（以前の 17 種類の名前）が残っていたら、承認は `stale` と同じ扱いで失敗にする（メッセージは「この操作は依頼では受けられません: <op>（画面で行ってください）」）。`propose` も同じ検査で拒否する。保存済みのデータの検証（`validate`）は、`OP_KINDS`（17 種類）を受けるので、古い依頼が残っていても保存できる。
- `--cause` は提案全体で 1 つ。原因が複数あるときは「その他」。
- 開始日のあるタスクに前のタスクを足しても、開始日は変えない（警告も出さない）。
- 提案のあとにデータが変わったときは、反映せず、依頼が「失敗」になる。「もう一度提案してもらう」で作り直す。先に Claude Code の画面で承認・却下した依頼を、HTML でもう一度承認しても、何も変わらない（二重には反映されない）。
- 期限を動かす `moveDue` と、`businessDays` 指定の `addTask` は、同じ依頼にできない。`planOps` が例外を投げる（前のタスクの期限が動くと、営業日が吸収されるため）。`agents/inbox.md` は、期限の移動だけを提案し、登録は承認後にもう一度依頼してもらう。`moveDue` と `due`（日付）指定の `addTask` は一緒にできる。

### 登録（`addTask`）の期限

- `due`（日付）か `businessDays`（営業日の整数）のどちらか一方。`businessDays` は 3650 日（約 10 年）まで（`dueAfter` が 1 日ずつ数えるので、打ち間違いで止まらないようにする）。
- `businessDays` は、完了していない前のタスクの期限の最大値（無ければ今日）から数えて、土日と休みを除いた日数後の日付になる。計算は `core/dates.js` の `dueAfter(base, businessDays, cal)`。
  - `cal` は `core/holidays.js` の `calendarOf(settings)`（`{off, on}`）。
  - `on`（`workdays`）の日は営業日、`off`（`holidays` と `nationalHolidays`）と土日は飛ばす。`on` が最優先。
  - `settings.countWeekendsAndHolidays` が `true` のときは、`calendarOf` が `off` を `holidays` だけにし、`countWeekends: true` を足す。`dueAfter` は `countWeekends` が `true` なら土日を飛ばさない。
- 営業日の計算は受信箱の登録だけで、期限の移動（`moveDue`）とドラッグの期限変更は暦日のまま。
- `propose` が `businessDays` を `due` に置き換えて提案の `ops` に保存するので、承認が翌日以降でも `stale` にならない（提案の表の `add` 行には `businessDays` が残る）。
- HTML の提案カードの登録の表には、行番号（`data-row`）と営業日の列が出る。「修正を依頼する」は暖色（`btn warm`）。

### 見張りと競合

- `tools/inbox.js submit ... --working` は、依頼を `working`（処理中）で作る。`wait` は `pending` だけを知らせるので、`/project-board:watch` が動いていても `inbox` エージェントに横取りされない。
- `/project-board:watch` は、Claude Code の Monitor で `node tools/inbox.js wait` を動かす。30 分ごとに終わるので、そのたびに再起動する。見張りが止まると、90 秒ほどで、帯が「見ていません」になる。
  - 作業中の Claude Code が、依頼のイベントを受け取って動くことは確認済み。
  - Claude Code が入力待ちの間に自動で起きることは、未確認。確認できないときは、作業中の Claude Code に「届いている依頼を処理して」と頼む（手動の入口のコマンドはない）。
- `wait` が出すイベントは `request` と `end` だけ。見ている印を書けないとき（`data.json` が検証に通らない、など）は、何も出さず、次の回にもう一度書く。HTML で承認・却下されたことも、知らせない（利用者は HTML で見ている）。見送った理由: 知らせても利用者の操作が要らず、`warn` は原因を伝えるだけで、帯の「見ていません」と、画面を開いたときに出るバナー（`validate` の注意）が原因を示す。
- 保存の競合: Claude Code が、受信箱や見ている印（30 秒ごとに更新）を書くので、画面での編集と、ファイルの更新が重なることがある。そのときは、画面が最新のファイルを読み直して、同じ編集を当ててから、もう一度保存する（編集は消えない）。

## 補助コマンド

プラグインとして使うときは、エージェントとコマンドが呼ぶので意識する必要はない。このリポジトリを直接開いて手で実行する場合の例（`plugins/project-board/` で実行する。`data/data.json` は `data/sample.json` のコピーで、gitignore 済み）。

```
node tools/validate.js data/data.json                  # 検証（errors があれば終了コード 1）
node tools/init.js [--sample]                          # 作業フォルダに project-board.html と .project-board/data.json を用意する
node tools/intake.js                                   # 取り込み・会議の規則・WBS の列の対応のコマンド一覧
node tools/inbox.js                                    # 受信箱（HTML からの依頼）のコマンド一覧（wait・claim・propose・approve など）
node tools/holidays.js <update|status> <data.json>     # 日本の祝日（内閣府の一覧）を取得して settings.nationalHolidays に保存／取得状況を表示
node tools/mcpconf.js --data <保存先> show             # 予定表の MCP の指定（保存先は PROJECT_BOARD_HOME でも指定できる）
node tools/doctor.js --data <保存先>                   # 動作環境の診断のみ（Node・保存先・祝日の接続・Excel・予定表の MCP。必須が足りなければ終了コード 3）
node tools/xlsx.js doctor --data <保存先>              # Excel 用の環境の診断のみ（Python のパスと置き場を表示。使えなければ終了コード 3）
node tools/xlsx.js setup [--system] [--yes] --data <保存先>   # 環境を作る（既定は専用の venv、--system はシステムのユーザー領域。--yes なしは入れ先と内容を表示して終了コード 3）
node tools/xlsx.js --data <保存先> plan.xlsx           # Excel を JSON で読む（Python と openpyxl を使う。環境が使えないときは終了コード 3）
```
